# Native torrent destination protection

Native torrent payload paths are opened through an [OS-enforced Go filesystem root](https://pkg.go.dev/os#Root). Per-torrent directory roots are anchored beneath the configured download folder. An existing link or non-directory at the torrent root, an existing symbolic-link directory component, and a non-regular final file are refused. Root-relative operations also prevent a path from escaping while it is resolved.

New payload files use exclusive creation and are sized only after their new file handle has been verified. Existing regular files are reused only at the expected size and after checking that the opened handle still identifies the inspected file. A conflicting file is retained instead of truncated. Existing hard-linked files are refused by checking the opened file's link count on Windows, Linux and macOS. These checks do not establish that arbitrary preexisting bytes are valid torrent content; torrent piece verification and the saved bitfield still govern completion/resume.

The app reports an actionable storage-conflict message without exposing a hard link's external target. Original files are retained, and transfer removal continues to keep data. Recover or choose a separate download location rather than deleting or overwriting the original as an automatic repair. A crash during creation may leave an incomplete new file; its size/type must pass the same checks before reuse.

Tests reproduced existing-file truncation and writable hard-link acceptance before the fix. The patched implementation passes safe nested creation/resume, conflicting-file preservation, hard-link refusal, per-torrent-root link refusal and nested directory-link refusal. A real native-engine regression also verifies the failed transfer's status, redacted recovery message and unchanged original bytes. On this Windows workstation, hard-link and directory-junction checks passed; file symlink creation requires a privilege that was not enabled, so that one fixture is explicitly skipped. Linux/macOS hosted symlink outcomes must be checked separately. No OS developer-mode, signing trust or filesystem permissions were changed to enable tests.
